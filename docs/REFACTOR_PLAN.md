## 二、问题诊断：为什么变得"碎且冗余"

### 诊断 1：单体文件导致没有边界
45 个路由、183 个函数在一个文件里。改任何一处都要读 6,665 行上下文；
新人（或新的一轮对话）无法判断某个逻辑"已经存在了没有"，于是**重复实现**。

### 诊断 2：静默失败文化 —— 这是最贵的
235 处 `except Exception` + 107 处 `except: pass`。
**本次会话在这个项目上挖出的、因静默失败而长期潜伏的故障：**

| 故障 | 潜伏时长 | 为什么没被发现 |
|---|---|---|
| K 线补刷漏 `import kline_get` | **6 周** | `except: return 0` 让"报错"和"今天没数据"长得一样 |
| `all` 全量刷被 `hot` 饿死 | **长期** | "跳过本次"看起来像正常保护 |
| `python -c` 起的 cron 未自举 env | 长期 | Redis 写被静默跳过，线上读到旧缓存 |
| 龙虎榜 clist 502 | **29 次失败** | 只打一行日志，tab 空白也没人报警 |
| `sig_theme` 恒 False | **长期** | 信号为假也照常出名单 |
| `refresh_fund` 全失败不报错 | 长期 | mapping 为空时既不写也不打印 |
| `selfcheck.py` 自己连不上 Redis | **长期** | 健康检查自己坏了，所以以上全部没被发现 |

**这 7 条的共同点：失败不发声，于是"看起来正常"。**

### 诊断 3：前端无源码 → 只能打补丁，越补越碎
线上 762KB 压缩产物没有源码，每次改动只能：
`字符串替换 → 手工验证 → 换文件名 → 升 SW 版本`。
本次为了加 2 个信号名，就折腾了 0620/0621 两个版本。**这是不可持续的模式。**

### 诊断 4：双轨预测系统概念重叠
三档预测（`prediction_short/swing/long`）与麦唛 ICIR（Q1–Q5）**都在回答"买什么"**，
但：口径不同、验证不同、页面分开。用户看到两个 tab 都在给名单，**不知道该信哪个**。
实测结论也印证：麦唛 Q4 历史命中 ~57%（6 次样本），主预测超额 +0.42%/天（5 天）——
**两者应该合并成一个"决策"视图，标注来源与置信度，而不是并列两个 tab。**

### 诊断 5：数据源降级链重复 N 遍
`clist → 腾讯 → 新浪 → 同花顺` 这套降级逻辑，在 `quick_scan` / `run_evening_review` /
`refresh_fund` / `refresh_lhb` / `ak_spot_snapshot` / `realtime_scan` 里各写一遍，
**其中 3 个漏改过**（就是上面挖出来的那批故障）。

## 三、重构目标（可验收）

1. **后端**：单文件 6,665 → 入口 < 300 行，业务拆成 8–10 个模块；**行为不变**
2. **失败可见**：`except` 必须留痕，静默吞异常从 235 处降到 **< 20 处**（且每处注释说明为何可吞）
3. **数据源收敛**：所有行情/资金/行业取数走**唯一适配器**，降级链只写一次
4. **前端可维护**：有完整源码、能一条命令构建、功能与当前线上 **1:1**
5. **UI 重构**：7 个平级 tab → 4 个（决策/市场/复盘/我的），一屏一个决策
6. **零功能丢失**：以「功能契约清单」逐项验收（见 Phase 0）

## 四、分阶段方案

> 每个 Phase 独立可停、可回滚。**任一步失败不影响线上。**

### Phase 0 · 冻结基线 + 功能契约清单（1 天）

**动作**
1. 把当前线上产物（0621 + 后端 + crontab + Redis 结构）打**只读归档**
   → `archive/2026-10-18-baseline/`
2. 产出 **`docs/FEATURE_CONTRACT.md`**：把现有全部用户可见功能列成表
   （功能 / 入口 / 依赖 API / 数据源 / 验收方法 / 截图标尺）
3. 用 Playwright 对 7 个 tab 各拍**基线截图 + DOM 快照**，作为后续"功能不丢"的对照物
4. 记录**基线指标**：接口数 45、平均响应、首屏渲染时间、包体 762KB

**验收**：契约清单覆盖 7 个 tab 全部功能；截图可复现。
**风险**：无（只读）。

---

### Phase 1 · 后端分层（3–4 天，**行为完全不变**）

把 `predict_server.py` 按职责切成模块，**只搬不改**，每搬一个模块跑一次回归。

```
backend/
├── app.py                 # Flask 入口：仅注册蓝图 + 启动（<300 行）
├── core/
│   ├── config.py          # env 自举、常量、模式配置
│   ├── cache.py           # 统一缓存层（Redis 优先 + SQLite 回写 + 内存 memo）
│   └── log.py             # 结构化日志（替代 114 处 print）
├── sources/               # ★ 数据源适配器（降级链只写一次）
│   ├── quote.py           # 腾讯 qt / 东财 / 新浪
│   ├── kline.py           # ifzq / 东财 / 新浪 / 同花顺
│   ├── industry.py        # 东财 datacenter
│   └── fund.py            # 资金流
├── domain/
│   ├── signals.py         # compute_kline_signals (155 行) + 权重/有效性
│   ├── trade.py           # calc_trade_params (162 行)
│   ├── predict.py         # quick_scan / deep_analyze / full_scan
│   ├── mbm.py             # 麦唛 ICIR（吸收 icir_model/icir_scorer）
│   ├── review.py          # 盘后验证 / 超额 / 信号回测
│   └── market.py          # 市场温度 / 涨停池 / 龙虎榜 / RSI
├── api/                   # 蓝图：predict / market / review / user
└── jobs/                  # 定时任务入口（cron 调用）
```

**关键约束**
- 每个模块搬完后，用 Phase 0 的基线**逐接口 diff**（响应字段、数量、耗时）
- `except` 一律改为：记录 `key + 异常 + 样本`，并**上报计数**；确需吞掉的写注释说明
- 服务器 2 核 2G：**迁移期间不在服务器上跑构建/测试**，全部本地验证后 scp

**验收**：45 个接口响应与基线**逐字段一致**；`predict_server.py` 降为薄入口。

---

### Phase 2 · 数据层收敛 + 失败可见（2–3 天）

1. **统一缓存层** `core/cache.py`：所有 `_REDIS.` 直连（48 处）收敛为一套 API
   （自动 TTL 策略、缺失告警、命中率统计）
2. **统一数据源适配器**：降级链只写一次，任何一源失败都**计数 + 告警**
3. **失败上报**：所有"降级/空结果"写入 `sm:health:errors` 计数，
   并在 `/api/health` 暴露：近 24h 各数据源失败次数
4. **自检升级**：`selfcheck.py` 已经是好的开始，纳入"数据源健康 + 卡死进程 + 数据新鲜度"，
   加一条 cron 每日 08:00 跑，失败**主动告警**（企业微信/邮件，任选）

**验收**：人为断掉一个数据源，`/api/health` 立刻能看到失败计数，且接口仍返回可用数据。

---

### Phase 3 · 前端源码化（5–7 天，**这是最大的坎**）

现状：`src/` 只有线上 **48%** 的功能。两条路：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | 以 `src/` 为工程基线，按 `FEATURE_CONTRACT.md` **补齐缺失的 ~52%** | 得到干净、可维护、可重构的真源码 | 需精确知道缺什么 |
| B | 从 `dist-pretty-v55.js` + `.recon/_pages/` **反推**成源码 | 与线上 1:1 | 反推代码可读性差，等于把"碎"固化 |

**推荐 A**，理由：
- `src/` 是**真源码**，能构建、有测试（`liveEngine.test.js`）
- `.recon/_pages/` 已经提供了缺失部分的**可读参照**（predict_pretty 99KB、backtest_pretty 44KB…）
- 反推代码虽然 1:1，但会把现有的"碎"原样继承下来，违背重构初衷

**具体步骤**
1. 补齐缺失功能：**量化 tab（麦唛）**、**复盘**、**估值分位/两融**，逐个对照 `.recon/_pages/` 实现
2. **每个功能补齐后立即用 Playwright 与基线截图比对**（布局/字段/交互）
3. 建立**构建发布流程**（一条命令）：
   `npm run release` → 构建 → 自动改名 `index-quant{ver}.js` → scp → 切 index.html → SW 版本 +1 → 冒烟测试
4. 清理 `/var/www/.../assets/` 的 40+ 历史文件（**移到 archive 目录，不删**）

**验收**：新构建产物与基线**逐 tab 截图比对通过**；包体 ≤ 基线（762KB）。

### Phase 4 · UI 信息架构重构（用户最关心，5–8 天）

#### 4.1 现在的问题

**7 个平级 tab，手机上底部栏挤满**，且语义重叠：

```
总览 | 预测 | 量化 | 股票 | 涨停 | 持仓 | 回测
        ↑     ↑            ↑          ↑      ↑
      都在给名单     看行情    看盈亏   验策略
```

- **「预测」和「量化」并列** → 两套模型都给名单，用户不知道该信哪个
- **信息密度过高**：单屏塞了分数、信号、入场、止损、目标、连板、行业、RSI、换手
- **颜色噪音**：涨跌红绿 + 多色标签 + 各种徽章，视觉上无法聚焦
- **无决策引导**：看完 7 个 tab 仍不知道该"买不买、买多少"

#### 4.2 建议的新结构：**3 层 + 4 tab**

```
底部栏（4 个，拇指可达）
┌─────────┬─────────┬─────────┬─────────┐
│  🎯 决策  │  📊 市场  │  📈 复盘  │  👤 我的  │
└─────────┴─────────┴─────────┴─────────┘
```

**① 🎯 决策（L1，一屏回答三个问题）**

| 区块 | 内容 | 数据来源 |
|---|---|---|
| **能不能买** | 市场阶段 + 建议仓位 + **实际市场暴露**（beta 0.45）+ 一句话结论 | `/api/env` `/api/position-advice` |
| **买什么** | 精选名单（麦唛 Q5 ∩ 预测 Top20 合并去重，**每只标注来源与置信度**） | `/api/mbm-predict` `/api/predict` |
| **买多少** | 按 beta 与波动给出每只的建议权重 | 新增 |

> 这一屏就是现在「预测」+「量化」的**结论合并**，把两套模型的分歧直接摆出来：
> 「麦唛说有、预测说没有」的股票单独标注为**分歧标的**，比两个 tab 各看一遍有用。

**② 📊 市场（L3，看环境）**
- 情绪：涨跌家数 / 涨停 / 炸板率 / 连板高度 / 板块热力
- 资金：主力净流入榜 / 龙虎榜（净买 + 机构）
- 机会扫描：实时 8 类信号（涨停/拉升/量比/换手/主力/超大单/反包/出货）
- RSI 扫描：超卖 / 超买 / 中位

**③ 📈 复盘（L4，验证与校准 —— 这决定你能不能进步）**
- **累计超额曲线**（策略 vs 全市场，含 beta）
- **信号有效性**（哪些信号真赚钱、哪些是拖累，正负分色）
- **模拟账户**（照 entry/stop/target 执行的结果 + 离场结构）
- **我的实盘 vs 系统建议**（Phase 5 上线后）

**④ 👤 我的**
- 持仓（含浮盈亏、**已实现盈亏**、净值曲线）
- 自选
- 设置（模式、通知、数据源状态）

**个股工作台**：从任意列表点进去，独立全屏页（不再是 tab）
- 顶部：K 线（可切日/周/月）+ 分时
- 中部：**信号面板（按有效性排序 + 正负分色）**、入场/止损/目标可视化在 K 线上
- 下部：行业、连板、资金、RSI、估值分位、同类对比

#### 4.3 视觉重构原则

| 原则 | 具体做法 |
|---|---|
| **一屏一个决策** | 决策页只放结论；细节全部点进去 |
| **降低颜色噪音** | 只保留：涨=红、跌=绿、警示=黄；信号标签改为**两级灰度 + 正负角标**，不再七彩 |
| **数字优先，文字其次** | 关键数字放大 2 倍；解释性文字默认折叠 |
| **正负可见** | 信号标签带 `+/-/·` 前缀（后端已下发 `sig_pn`） |
| **拇指热区** | 主操作（加自选/看K线）落在屏幕下半 60% |
| **骨架屏 + 空态** | 所有异步区块有骨架屏；无数据时明确说"为什么没有"（如"非交易时段"） |
| **深色为主** | 保留现有深色，统一色板为 1 主色 + 2 语义色 + 4 灰阶 |

#### 4.4 技术选型建议（不引入重依赖）
- 保持 **Vue 3 + Vite**（现有栈，`node_modules` 已就绪）
- **不引入 UI 框架**（Element/Vant）—— 体积敏感，且现有 CSS 87KB 可复用
- 图表：`lightweight-charts` 已有；新增的曲线图用**内联 SVG**（零依赖，如 `/api/report` 那样）
- 路由：从"tab 切换 + v-if"改为 **Vue Router**（hash 模式，免 nginx 配置），支持深链接

**验收**：4 个 tab 的截图评审通过；首屏 JS ≤ 基线；一屏内完成"今天买不买"的判断。

### Phase 5 · 让系统帮你进步（2–3 天，新能力）

前面几轮已经证明：**系统能选股，但不能告诉你"你做得怎么样"**。这是投资收益提升最大的一环。

1. **交易记录**：`/api/trades`（买入/卖出/已实现盈亏/手续费）
2. **实盘 vs 建议对比**：系统说买 A 你买了 B，结果差多少
3. **你的净值曲线** vs 系统模拟账户 vs 全市场基准
4. **卖出决策**：持仓触及止损/目标时**主动提醒**（PWA 通知或每日摘要）

## 七、需要你先拍板的 3 件事

1. **Phase 3 走 A 还是 B？**
   - **A（推荐）**：以 `src/` 为基线补齐功能 → 得到干净源码，但补齐过程需逐项比对
   - B：从产物反推 → 与线上 1:1，但把现有"碎"固化下来

2. **UI 重构的激进程度？**
   - **保守**：保留 7 tab，只重排布局、统一色板、加决策引导（3–4 天，风险低）
   - **推荐**：改成 4 tab 三层结构（5–8 天），需要你认可新的信息架构
   - **激进**：连交互范式一起换（卡片流 + 语音/快捷指令）

3. **Phase 5 的交易记录要不要做？**
   这需要你**每天录一次持仓**（或接入券商导出）。不做的话，系统永远只能告诉你"该买什么"，
   无法告诉你"你执行得怎么样"——而后者对收益的影响往往更大。
